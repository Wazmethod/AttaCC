# V1.1 — SteamPlant compatibility audit

**Status:** source review and incremental compatibility changes; SteamPlant has **not** been converted to the unified SDK.

## Current SteamPlant data flow

- `apps/steamplant/telemetry.lua` calls legacy `lib.io`, controller state and module device methods, and assembles a `module_telemetry` message.
- This includes nested fields: plant.status; power.rpm/rawRpm/stress/capacity/load/overstressed; boiler.level/size/water/heat; battery.energy/capacity/percent/maxInsert/maxExtract; motor.rpm/direction/consumption/stressCapacity; control.state/error/automatic/armed/offline/clutch states.
- `apps/steamplant/main.lua` distributes telemetry on configured modem channels, routes module commands, and separately calls `webcap.publish("steamplant", ...)` for monitor/page/module state and latest event. This is **not** the proposed per-field SDK data/graph/control/view descriptor.
- `apps/steamplant/view.lua` uses `lib.display.renderer` with app-specific `lib.ui` and `lib.ui_graphics`, and a touch transform for the angled3/mirror_x monitor profile.
- Text renderer provides control, generator, data, event and debug pages. Graphics renderer includes dashboard, graphs, events, machine and debug views, sampling local graph history and compact layout paths. Exact options are configured in `config.display`.
- Current UI touch actions include page selection, explicit backend switch and module command dispatch. A direct migration to generic `lib.display_sdk` today would lose existing layout/detail.

## Compatibility strategy

1. Preserve the current `app.steamplant` behavior, `lib.io` access, telemetry payload and `lib.ui` / `lib.ui_graphics` paths while adding an SDK descriptor adapter.
2. Map telemetry fields to stable `app:data` names. Define a separate `app:graph`/series API for RPM/load/battery history (currently missing from V1.1 facade).
3. Provide a consistent public `app:control` action representation and server-side validation. Do **not** attach remotely supplied strings directly to Lua callbacks.
4. Model the current page/tabs, configuration flags, debug details and historical graphs as views; allow SteamPlant to opt into the **existing rendering adapter** until the generic renderer can reproduce it.
5. The physical monitoring/control integration currently uses `lib.io`, not the new `io_registry` facade. Introduce migration mappings and explicit `required` contracts before removing compatibility.
6. Preserve the per-monitor touch transforms `normal`, `mirror_x`, `angled3` through Display options; preserve optional monitor behavior and graphics fallback.

## Display mode-switch infrastructure implemented in this slice

- Generic `lib.display.renderer` now exposes `availableBackends()` and `toggleBackend()`, reusing existing `setBackend()` and compatibility fallbacks.
- SteamPlant's existing display wrapper exposes these methods without changing its current text/graphics UI.
- The V1.1 facade offers `app:renderer(options)` for apps that supply dedicated backends. **This does not make `app:draw()` CC:Graphics-ready**: `app:draw()` still uses the generic text-first `lib.display_sdk`.
- A future generic renderer can expose the same mode switching with shared navigation and theme.

## Release discipline

Keep this work on `feature/v1.1-sdk-unification`. No changes to SteamPlant's existing telemetry, control, monitor touch logic or app-specific rendering should be merged without in-game testing against the existing save. Current slices are pushed but not tested in Minecraft.
