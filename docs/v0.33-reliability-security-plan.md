## Important security distinction

Checking the `network`, `origin`, command age and message shape is a **sanity check**, not network authentication. Any nearby computer able to transmit modem messages could forge these values. For Minecraft gameplay this is often an acceptable starting point, but we must not claim it authenticates senders. Do not treat modem-transmitted origin strings as secret or trusted.

For sensitive commands, consider an explicit per-world shared secret or a pairing workflow in a separate, opt-in change if playtesting indicates a need.

## Tests on a spare SteamPlant / Master setup

1. Run a valid remote command and confirm the Master receives the same result as before.
2. Disconnect the wireless modem and reconnect it; ensure handlers recover.
3. Test stale timestamps and wrong network through the optional validator before connecting it to a live handler.
4. Try an invalid package path from a test manifest; it must be rejected without overwriting protected files.
5. Update a normal app/module with `pkgctl update` to verify the existing package format remains compatible.

Avoid testing safety commands against an important live contraption. No dedicated test-suite execution has been performed in the game yet.

## Scope adjustment

User intentionally excluded (1) automatic modem reconnect and (2) duplicate-command suppression. Focus: (3) useful error logs and (4) startup verification. `core/runtime.lua` now rotates journal and per-component logs at 64 KiB, preserving `.1`. `core/startup.lua` logs startup events and missing programs/presets; logging failure does not block boot. `core/logctl.lua` provides `logctl tail`, `logctl errors`, `logctl health` and optional counts/components. The manifest now ships the new command via `core.runtime`.

## Boot health and log viewer

The `logctl.lua` program is delivered with `core.runtime`, so a package update installs it as `logctl`. The startup bootstrap records information about the selected preset and missing programs in `/var/log/attacc/`, and publishes a `startup` status entry to the local runtime state. For standard computers, an application returning failure is also recorded. A successful `shell.openTab` does not establish that a GUI app will remain running; the status means the startup configuration was accepted, not a full application heartbeat.

Test on an ordinary spare CC: `pkgctl update core.runtime`, `reboot`, `logctl tail`, `logctl health`, `logctl errors`. Also try an invalid `/etc/preset` to confirm a readable error; restore it afterwards. The component logs are bounded and retain a single previous rotated file.
