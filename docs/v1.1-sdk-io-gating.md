# AttaCC V1.1 — SDK I/O resolution and control gating

This note documents the V1.1 development branch. SteamPlant remains on its
existing I/O adapter until functional parity is verified.

## Declare hardware

```lua
local app = require("lib.attacc").app("example", { title = "Example" })

app:io("motor", {
    type = "electric_motor", required = true,
    direction = "output", label = "Generator motor",
})

app:io("display", {
    type = "monitor", required = false, label = "Optional display",
})
```

`app:hardwareStatus()` returns `statuses, ready`; `ready` is false only
when a required role is unavailable. The SDK uses the same resolver as
`ioctl check`: explicitly configured device, exactly one matching automatic
candidate, or a meaningful missing/ambiguous error. Redstone bindings validate
their configured side and relay presence.

## Gate individual controls

```lua
app:control("start", {
    label = "Start generator",
    requires = { "motor" },
    run = function()
        -- Runtime checks the declared motor before entering here.
        return app:write("motor", 64)
    end,
})

app:control("abort", {
    label = "Emergency abort",
    confirm = true,
    run = function()
        -- No automatic hardware prerequisite: keep recovery available.
        -- Application-specific safe shutdown logic remains responsible
        -- for handling failures and returning appropriate errors.
    end,
})
```

The `requires` list is per control (not a global blockade). It must
reference roles declared with `app:io`. A missing or ambiguous role causes
`app:invoke` to return `false, reason` without calling the action.
The descriptor also marks that control as disabled so UI clients can reflect
its current availability.

`app:read(role)` and `app:write(role, value)` continue to use configured
logical bindings in `/etc/io.lua`. A device being discoverable is **not**
sufficient to call its methods: configure `method`, `direction`, and other
binding fields where appropriate.

## Requirements discovery and ioctl

`app:publish()` persists the app's role declarations using
`lib.io_declarations` before exporting the descriptor. `ioctl init`
discovers those persisted declarations, combined with the legacy config
requirements. On a new installation, start/publish the SDK app once before
running `ioctl init`, or provide requirements through the legacy config.
An app can validate its own in-memory declarations before publication.

```text
ioctl hardware
ioctl init
ioctl check
ioctl show example.motor
```

Bindings are scoped by `<app-id>.<role>` for SDK apps. Persisted requirements
are a discovery cache, not an authentication or device-ownership mechanism.
Two apps can still contend for one physical peripheral.

## Migration and verification checklist

- Keep SteamPlant's existing sensor and actuator safety behavior unchanged.
- Declare all physical roles, their direction, and their required/optional state.
- Configure each callable logical I/O binding with `ioctl init`.
- Add `requires` to controls that must not run without particular equipment.
- Leave emergency actions independently available.
- Verify exactly one device, zero devices, and multiple matching devices.
- Verify peripheral detach/reattach, disabled optional roles, invalid redstone
  sides, and missing relays.
- Test actuator methods, scaling/inversion, restored outputs, interlocks,
  automatic start/stop, and network supervision **in game** before switching
  SteamPlant to the SDK.
- Remote command transport and authorization are not implemented by this change.
