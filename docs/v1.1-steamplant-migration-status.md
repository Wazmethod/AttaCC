# AttaCC 1.1 — migration SteamPlant vers le SDK

Branche de travail uniquement. Ne pas installer sur une machine de production.

## Implémenté

- `core/io_catalog.lua` découvre des contrats matériels installés sous
  `lib/attacc_requirements_<id>.lua`, sans démarrer l'application.
- Le manifeste installe le contrat `steamplant`; `ioctl init` et
  `ioctl check` peuvent lire les rôles SDK avant la première publication.
- `ioctl init` conserve les méthodes, arguments, transformations et
  paramètres Redstone des bindings existants pendant leur réaffectation.
- La résolution matérielle ne réaffecte plus silencieusement un périphérique
  explicitement nommé lorsqu'il disparaît.
- `apps/steamplant/sdk.lua` déclare les données, graphes, commandes,
  vue générale et maintenance avec les primitives `lib.attacc`.
- Le module SteamPlant enregistre ses rôles et actualise les données du SDK
  parallèlement à son protocole existant. Le contrôleur conserve ses interlocks
  et sa logique de démarrage/arrêt.

## Limites actuelles — pas encore « full SDK »

1. Les méthodes des périphériques sont encore appelées dans
   `apps/steamplant/io.lua` par le code de contrôle historique.
2. L'initialisation I/O demeure partiellement liée à la configuration
   spécifique SteamPlant, notamment les embrayages Redstone.
3. Les commandes réseau passent encore par la logique du contrôleur et
   le protocole historique; il manque un chemin AttaCC générique et son
   mécanisme d'autorisation.
4. Le rendu local et certaines vues réseau conservent leurs anciens adaptateurs.
5. Le contrat SDK doit encore exposer toutes les variantes de commandes,
   tous les événements, protections et états, avant suppression des chemins
   hérités.

## Ordre de migration restant

1. Déclarer des rôles logiques de lecture et d'écriture pour chaque capteur,
   moteur et embrayage, puis configurer leurs méthodes et transformations.
2. Remplacer les appels matériels directs de SteamPlant par
   `app:read` / `app:write` ou les primitives I/O communes.
3. Introduire un transport de commandes AttaCC avec filtrage machine/réseau,
   identifiants de requête, anti-doublons, acquittements et autorisation;
   réutiliser le même dispatch local qu'en UI.
4. Remplacer les publications de télémétrie et d'événements historiques par
   les messages standard du SDK, avec compatibilité Master/Pocket/Web.
5. Migrer les vues et le cycle de vie vers le runtime SDK; supprimer le code
   spécifique devenant redondant.
6. Effectuer revue statique, contrôle des manifests et validations hors jeu.
7. **Seulement lorsque le portage complet est terminé**, organiser les tests
   sur les ordinateurs CC en vérifiant la parité fonctionnelle.

Ne pas présumer que les protections d'une machine sont garanties par
`requires` : cette option vérifie la présence matérielle, pas la sûreté d'une
commande ni l'authenticité de sa provenance.


## Migration lot: SDK I/O + network envelope (October 2026)

- SteamPlant sensor reads use `app:call(role, method, ...)`, resolved through
  the shared registry; motor `setSpeed`/`stop` use the same SDK API.
- Three clutch outputs use `app:write()` with role-specific inverted redstone
  mappings, and `app:read()` for physical output state.
- A shared SDK command dispatcher accepts `attacc.sdk.command.v1` envelopes
  and responds using `attacc.sdk.ack.v1`. It validates app, target, logical
  network, request freshness, origin, remote-enabled control and request ID.
  It caches results to avoid repeating identical accepted requests.
- SDK commands arrive on `sdkControl` (4257) with acknowledgements on
  `sdkAck` (4258); existing Master/Pocket command channels remain unchanged.
- **Remote execution is intentionally disabled** until real authenticated
  sender authorization exists. Any request on the SDK channel is rejected.
  The legacy protocol has not been authenticated or replaced by this work.

### Remaining work before full SDK

1. Introduce authenticated sender identities/capabilities, with a defined
   provisioning, revocation and replay-resistance model.
2. Migrate Master, Pocket and Web clients to send SDK envelopes, consume
   acknowledgements and discover SDK descriptors.
3. Move legacy UI events/telemetry and application lifecycle fully onto SDK.
4. Validate configuration and peripheral routing by offline test harnesses,
   then conduct final in-game parity tests only after full migration.
5. Retire legacy command handlers and I/O compatibility after verification.

Never enable remote actuator controls by merely allowing network names,
origin strings or matching computer IDs.


## SDK network migration — authenticated transport (October 2026, continued)

- Master and Pocket support opt-in HMAC-SHA256 SDK command envelopes. Missing
  client configuration preserves legacy behavior; **invalid enabled client
  configuration does not silently downgrade**.
- SDK server checks per-peer allowlisted controls and a signed canonical
  request payload, and signs its ACK. Clients validate the ACK's signature,
  original control, target and request ID.
- Server operator can explicitly disable legacy remote commands by configuring
  `legacyCommands=false` in `/etc/sdk-auth.lua`. This is **not the default**
  until all Master/Pocket/Web command senders have migrated.
- AttaCC bundles pure-Lua SHA-256 instead of depending on an undocumented
  ROM hashing API. `tests/sdk-crypto.lua` contains reference hash vectors
  and a request-tampering test, **not yet executed**.

### Still outstanding

- Runtime tests for the new auth module and independent crypto vectors.
- Credential provisioning/rotation and versioned policy migration tooling.
- Master/Pocket SDK descriptor/telemetry discovery and Web bridge command
  migration, not just the command sender.
- Full SDK-owned app lifecycle, event streams and UI rendering.
- Retiring legacy protocols completely and end-to-end parity validation after
  the full SDK application migration.


## SDK discovery, monitoring and compatibility (October 2026)

- Generic `lib.sdk_snapshot` provides the public `attacc.sdk.snapshot.v1`
  envelope and a compatibility adapter to existing UI model data.
- SteamPlant now transmits its SDK descriptor on channel **4259**
  (`sdkSnapshot`) in addition to historical module telemetry.
- Master discovers apps by SDK descriptor, prioritizes SDK snapshots over
  duplicate legacy telemetry and forwards adapted data to Pocket.
- Pocket direct transport can also consume generic SDK snapshots and
  discover multiple SDK apps; Master transport continues to use the
  aggregated app list during migration.
- Snapshot wire data omits local hardware configuration and only includes
  the latest graph sample. Historical UI trends are rebuilt from snapshots.
- `tests/sdk-snapshot.lua` exercises generic discovery, compatibility,
  public-data filtering, command visibility and graph projection.

### Not yet production-ready

The compatibility layer is transitional: native descriptor-driven Master,
Pocket and Web views, unified lifecycle/events, application-neutral publisher
integration and complete legacy removal remain unfinished. Snapshot and
cryptographic tests have been added but **not executed in CraftOS**. SDK
snapshots currently do not authenticate telemetry or provide confidentiality.


## WebBridge SDK transport and descriptor views

- WebBridge now subscribes to SDK snapshots (4259) and forwards
  `sdk_snapshot` messages with both raw public SDK descriptors and a
  backwards-compatible display projection.
- Web-origin commands may use signed SDK requests through the same
  opt-in client policy as Master/Pocket, and SDK ACKs are verified before
  forwarding to the WebSocket.
- SDK view definitions are now carried by the generic snapshot envelope;
  this enables future descriptor-based renderers without SteamPlant-specific
  page models.
- Missing target identity is a configuration error in signed SDK mode;
  do not downgrade to unauthenticated legacy commands.
- Web server/frontend must still be updated to natively consume snapshots,
  and full SDK event/lifecycle replacement remains outstanding.
- No runtime/Lua host verification or in-game validation was performed.


## SDK public facade and generic host (October 2026)

- Added `lib.sdk_facade` behind the existing single public
  `require("lib.attacc")` entry point. Public app APIs:
  `app:requirements()`, `app:device()`, `app:output()`,
  `app:config()`, `app:require()`, `app:checkDependencies()`.
- Added `app:run()`, backed by `lib.sdk_host`, with an initial
  **standalone/local** CraftOS event loop, publishing, dependency and
  hardware checks, SDK display/touch handling and clean shutdown.
- SteamPlant SDK adapter now registers the static hardware contract through
  `app:requirements()`, rather than manually reimplementing declaration.
- Fixed `app:invoke()` to propagate explicit `false, error` results.
- Added `tests/sdk-facade.lua` (not yet executed) and
  `docs/sdk-app-development-v1.1.md`.

**Not yet full SDK:** SteamPlant `main.lua` still hosts network, display,
runtime and node administration directly. The new host does not yet
replace these services. Controller and other SteamPlant modules still
contain legacy infrastructure imports. Continue moving those capabilities
behind SDK services before deleting any existing host or deploying to CC.


## pkgctl et arborescence applicative (V1.1)

Le manifeste installe maintenant SteamPlant, Master, Pocket, Workstation et Dashboard dans leurs dossiers `apps/<id>/` en conservant temporairement les copies historiques. `pkgctl` interdit les écritures inter-applications dans cet espace. Le catalogue des requirements consulte d'abord `apps/<id>/requirements.lua`, puis l'ancien chemin `lib/` comme solution de repli. Voir `docs/sdk-package-layout-v1.1.md`.

Il reste à migrer les chemins d'exécution et les imports métier avant de retirer les anciennes copies. Aucun test d'exécution effectué.


## Chargeur d'applications SDK et pkgctl

Ajout de `core/app_loader.lua` et `core/tools/appctl.lua`, installés par `core.runtime`. Un programme SDK natif réside dans `apps/<id>/main.lua`, retourne son objet `attacc.app`, utilise `require("lib.attacc")` et charge ses modules métier localement via un `require` propre à l'application. `pkgctl run <id>` lance uniquement les apps enregistrées comme installées. Les `main.lua` legacy ne répondent pas encore à ce contrat et ne doivent pas être lancés par `appctl` avant migration. Documentation : `docs/sdk-app-loader-v1.1.md`. Aucun test d'exécution en jeu.
