# AttaCC V1.1 — Unified Developer SDK

**Status:** design and implementation branch created from `dev` following Web polish PR #10. Not merged into `dev` or `main`.

## Product goal

Applications should use **AttaCC APIs** to declare their state, hardware, local UI and remote controls, rather than re-implementing bespoke CraftOS screens and per-app network messages.

An elevator app, for example, declares **three buttons** (floor 1/2/3), **two data items** (current floor / motion), and optionally history series. AttaCC clients render the same declaration as a local monitor dashboard and as machine DATA / GRAPHS / CONTROLS for Master, Pocket and Web.

## Clearly separate platform APIs

| Layer | CraftOS / CC:Tweaked primitives | Existing AttaCC layer | V1.1 responsibility |
|---|---|---|---|
| Lifecycle | `shell.run`, `os.pullEvent`, `os.queueEvent` | `lib.runtime`, `lib.bus`, startup presets | Common app lifecycle helper / error reporting |
| Networking | `peripheral.find('modem')`, `modem.open`, `modem.transmit` | `lib.network`, `lib.protocol`, `lib.nodes` | Command handlers, replies, telemetry publication; explicit safety boundaries |
| Hardware | `peripheral.wrap`, `redstone.*` | `lib.io_registry` | Typed bindings, validation and uniform access |
| Display | `term`, monitor peripherals, CC:Graphics | `lib.display`, `lib.display_graphics`, `lib.display_api` | Standard widgets, layouts and consistent input routing |
| Pocket | Pocket terminal and optional monitor | `apps/pocket/view.lua` -> `lib/pocket_display.lua` | Preserve hybrid Pocket behavior; share widget/data schema |
| Web export | JSON, HTTP bridge | `lib.webcap`, app UI descriptor telemetry | Make DATA / GRAPHS / CONTROLS descriptors easy to declare |

`lib.pocket_display` is currently **application-specific**, not a `module.display_pocket` package. Reuse its behavior without breaking Pocket.

## Desired authoring API (proposal, not implemented)

```lua
local attacc = require("lib.attacc") -- planned facade, not in V1.0.0
local app = attacc.app("elevator", { title = "Lift", requires = { "core.runtime" } })

app:data("floor", { label = "Floor", read = function() return 2 end })
app:data("moving", { label = "Moving", read = function() return false end })

app:control("floor_1", { label = "Floor 1", run = function() end })
app:control("floor_2", { label = "Floor 2", run = function() end })
app:control("floor_3", { label = "Floor 3", run = function() end })

app:view("main", {
  layout = "dashboard",
  data = { "floor", "moving" },
  controls = { "floor_1", "floor_2", "floor_3" },
})
```

The actual API naming and schema must be validated against existing `ui.app`, `ui.groups`, `ui.controls` telemetry before implementation. Application commands must be validated server-side/on the machine; **the UI alone is not authorization**.

## Proposed work packages

1. **Inventory and compatibility:** diagram actual `lib.display`, `lib.display_api`, `lib.display_graphics`, Pocket adapter, network and existing UI descriptor schema.
2. **Single descriptor schema:** define metrics, series/graphs, controls, grouping, layout, status and view selection, with normalized IDs/types and a version field.
3. **AttaCC SDK facade:** wrap runtime, bus, I/O, network and display in a small Lua developer-facing API; no second parallel runtime.
4. **Local renderer:** implement generic terminal/monitor widgets and optional CC:Graphics fallback using current display modules, not app-specific copied views.
5. **Remote representation:** expose the same DATA / GRAPHS / CONTROLS to Master, Pocket and Web through existing telemetry/WebBridge paths.
6. **Pocket compatibility:** preserve text/graphics toggle, categories and optional external monitor while using generic view definitions.
7. **Examples:** a working elevator simulator with three buttons and two metrics, hardware-free mode, plus I/O-bound variant.
8. **English Web DOCS:** separate **CraftOS primitives** from **AttaCC public API**, with signature, examples, errors, behavior, limitations and usage for every API. Add per-binary manuals as needed.
9. **Validation:** regular/Advanced/Pocket computers, disconnected modem/monitor, touchscreen/click actions, pagination, reboot and WebBridge.

## Compatibility and release rules

- Keep `main` unchanged while V1.1 is developed.
- Implement changes **only on this feature branch**; merge into `dev` once tested and approved.
- Preserve current V1 apps, packages, paths and `core.runtime` version semantics.
- Do not couple package/version metadata to the application UI schema.
- Do not silently route network commands to arbitrary handlers or claim protocol timestamps authenticate senders.
- Migrate native applications directly to AttaCC SDK after the public APIs cover their complete behavior; use a test-first staged cutover, not permanent compatibility adapters.

## Acceptance criteria

- A new app can be written using public AttaCC APIs without copying SteamPlant/Pocket rendering logic.
- A 3-button / 2-data elevator dashboard works on a bound local monitor and exposes remote DATA/GRAPHS/CONTROLS using one descriptor.
- Optional hardware degrades gracefully and status/logs remain meaningful.
- Pocket hybrid display continues to work.
- API documentation and examples match real signatures and tested behavior.

## Architectural decision — Native API only (15 October 2026)

The goal is **full migration of native apps to public AttaCC SDK APIs**. Do not introduce or preserve per-app compatibility adapters as the final implementation. Each app will declare and operate through the shared API for data, graph series, controls, views, I/O and events; AttaCC owns rendering, touch mapping, navigation, resize behavior, backend selection, local and remote publication.

**Migration sequence:** finish the SDK contract and implementations first; then rewrite each native app directly against it on the V1.1 feature branch, validate feature parity (SteamPlant controller, telemetry, safety, history, pages, graphics, Pocket hybrid, networking), and remove redundant legacy renderer / transport code only after validation. Until then, unmodified apps keep running on their existing implementation in `main` and `dev`; this is staging, not an adapter layer.

Do not claim complete migration until hardware-in-the-loop and in-game tests are run. Maintain the existing visual information density and all supported actions, while applying the updated AttaCC design system.
