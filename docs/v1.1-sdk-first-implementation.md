# AttaCC 1.1 SDK — First Implementation

**Branch:** `feature/v1.1-sdk-unification`. This is an initial functional facade, **not** the completed declarative renderer or network control layer.

## Native CraftOS vs AttaCC

| CraftOS primitives | AttaCC facade |
|---|---|
| `os.pullEvent()` and `os.queueEvent()` | `app:on()`, `app:emit()`, `app:handle()` |
| `term`, monitors and CC:Graphics | `app:view()` declares a portable *descriptor*; automatic rendering not yet implemented |
| `peripheral`, `redstone`, `modem` | Existing `lib.io_registry` / `lib.network`; facade integration to follow |
| Plain Lua variables | `app:data()`, `app:set()`, `app:values()` |
| Function calls | `app:control()`, `app:invoke()` (local only) |
| CraftOS print/files | `app:log()`, `app:status()` |

## Minimal API

```lua
local attacc = require("lib.attacc")
local app = attacc.app("elevator", {title="Elevator"})
app:data("floor", {label="Current floor", value=1})
app:data("moving", {label="Moving", value=false})
app:control("floor_1", {label="Go to 1", run=function() app:set("floor", 1) end})
app:view("main", { data={"floor","moving"}, controls={"floor_1"} })
app:publish()
app:invoke("floor_1") -- local trusted Lua only
app:publish() -- push updated values; automatic reactivity is not yet implemented
```

## Actual implemented calls

- `attacc.app(id, {title=...})` creates an in-memory application descriptor.
- `app:data(id, {label, unit, value, read})` declares a metric. `read` is an optional callback invoked during snapshot building.
- `app:set(id, value)` updates a metric's stored value.
- `app:control(id, {label, description, run})` declares a local callback.
- `app:invoke(id, ...)` executes a **locally trusted** callback with error logging. Remote actions are **not** wired to this method.
- `app:view(id, {label, layout, data, controls})` declares a named view.
- `app:descriptor()` builds serializable data; no functions are exported.
- `app:publish()` publishes the descriptor via existing `lib.webcap` and optionally `lib.display_api` when the display package is installed.
- `app:on(topic, handler)`, `app:emit(topic, payload)`, `app:handle(event, ...)` wrap the current local event bus. Events still need explicit dispatch in the CraftOS main loop.
- `app:status(state, detail)`, `app:log(level, message)` wrap `lib.runtime`.
- `app:close()` unsubscribes local handlers and clears published data owned by this app.

## Explicit limitations

1. `app:view()` does **not** draw buttons to a monitor yet.
2. `webcap` publication does **not** automatically create WebUI widgets or remote controls.
3. `app:invoke()` must not be bound directly to untrusted network traffic. Authentication, target validation, limits and acknowledgments are a separate upcoming step.
4. Data must be republished when values change; automatic subscriptions are future work.
5. The descriptor is written by `display_api` with a single current owner. Multi-app composition is not yet implemented.
6. This does not change SteamPlant, Master, Pocket, Dashboard or other existing apps.

## Testing

Install the branch's `core.runtime` package on a **spare CC** using a test repository. Copy `examples/sdk-elevator/main.lua` to `elevator-demo.lua`, then run `elevator-demo`. Press 1/2/3, observe logs with `logctl tail 20 app:elevator`, and verify the published capability in the machine snapshot. Press Q to clean up. A monitor UI is not expected yet.

## Declarative display interactions (incremental V1.1)

The generic text renderer computes hitboxes from declared `control` nodes; applications no longer need to maintain button-coordinate maps. Its footer creates touch targets for pagination when more than one page exists; `app:touch(result, x, y)` updates `app.displayPage` and the caller redraws. Keyboard and monitor events still need a CraftOS event loop.

`display.toggle` is a **reserved action**, not an application business control. In a generic text view it is only rendered when both `graphicsAvailable = true` and `onToggleRenderer` (a functioning mode-switch callback) are explicitly passed to `app:draw()`. Do not enable this flag merely because the peripheral claims CC:Graphics support: a real graphics renderer must exist. Otherwise the mode button is hidden. Legacy apps can use `renderer:toggleBackend()` and `renderer:availableBackends()` independently.

Low screen resolution shows a warning and suppresses interactive controls rather than terminating the application. `app:draw()` returns a diagnostic status; optional monitor failures should be handled by falling back to `term.current()` or skipping display. Hardware role declarations through `app:io()` are metadata only until I/O binding integration is completed.

**Still pending:** generic CC:Graphics theme and renderer, I/O monitor binding, live graph widgets, remote controls, full SteamPlant screen migration and automated in-game validation.

## Graphs and control availability (V1.1 feature branch)

Applications now declare bounded numeric time series with `app:graph(id, {label, unit, limit})` and add points via `app:sample(id, number, timestampMs)`. The default cap is 60 samples (minimum 2, maximum 300). Non-numeric or non-finite values and invalid timestamps are rejected. Published descriptors carry a copy of each graph's `samples = {{timestamp=..., value=...}, ...}`. The text renderer shows the latest graph value; a real generic graphics/history plot is **not yet complete**.

Controls can define `enabled = true/false` or `enabled = function() return ... end`. The SDK checks availability before executing `app:invoke()`, and `app:descriptor()` publishes `enabled` for the UI. The generic text renderer labels unavailable controls and **does not register touch hitboxes** for them. `confirm = true` and `remote = true` are exported metadata only: confirmations, remote authorization and remote command dispatch are **not implemented yet**, and must not be assumed to protect dangerous machine actions.

```lua
app:control("start", {
  label = "START",
  enabled = function() return safetyReady and not running end,
  run = function() startPlant() end
})
app:graph("rpm", {label="RPM", unit="rpm", limit=120})
app:sample("rpm", currentRpm)
app:publish()
```

For native app migration, first match all existing sensors, commands, history and safety conditions in the SDK. No legacy rendering adapter is planned for the final V1.1 architecture. Keep V1 installations on their current software while validating the new public APIs on spare CCs.

## Generic CC:Graphics rendering — current integration

The V1.1 branch now bundles `lib.display_sdk_graphics` with `module.display`. `app:draw(target, {view=...})` selects the CC:Graphics renderer when the target offers `setGraphicsMode`, `drawPixels` and `setPixel`, and otherwise renders the same descriptor with the text renderer. `app:touch(result,x,y)` uses automatically generated hitboxes, including page navigation and the reserved `display.toggle` action; applications do not define pixel coordinates. If graphics initialization/rendering fails, the SDK attempts text fallback.

This is an **initial** renderer and still needs Minecraft testing, responsive layout refinements and true graph curves. Its graph widgets presently show the last sample. Hardware bindings and remote action transport are not yet integrated. Native apps have not yet been migrated.

## Banner and historical graph widgets

`app:graph(id, {label, unit, limit})` declares an exportable numeric series; `app:sample(id, number)` records a point. In **text mode**, a `{type="graph",id="rpm"}` node is rendered as a proportional bar and last numeric value. In **CC:Graphics**, the same node plots a connected line through the recorded samples (normalizing to the sample minimum/maximum, or declared `min`/`max` if available). The graphics plot is a first implementation and still requires in-game performance/resolution testing.

`app:banner(id, {label, value, read, scroll=true})` declares a horizontal text banner. `app:bannerValue(id, value)` updates a static banner; an optional `read=function() ... end` supplies the current value during snapshots. Include `{type="banner",id="notice"}` in a view's children. Both text and graphics renderer scroll content horizontally when longer than the available width. **Animation is timer-driven**, not background execution: call `app:tick()` periodically and redraw to advance scrolling. The existing Elevator example uses a CraftOS timer at 0.3 seconds. All banner values are published in the same SDK descriptor for future remote clients.

```lua
app:banner("notice", {value="SYSTEM READY - SELECT FLOOR"})
app:view("main", {children={{type="banner",id="notice"}}})
-- In a CraftOS timer event handler: app:tick(); app:draw(monitor,{view="main"})
```

The final unified UI layout and display/IO assignment remain under development. These commits modify only `feature/v1.1-sdk-unification`; do not deploy them onto production CCs yet.

## Persistent maintenance interface (presets and native applications)

A native app launched by a preset may expose a dedicated **text-mode maintenance tab** without implementing another TUI, coordinate map, or renderer. Declare it with `app:maintenance("maintenance", {label="Maintenance",children={...}})`. It uses the same `data`, `graph`, `banner`, and `control` nodes as all other SDK views. The alias `app:technical()` is retained on this development branch.

```lua
app:maintenance("service", {
  label="Service",
  children={
    {type="section",label="Status",children={{type="data",id="rpm"}}},
    {type="section",label="Commands",children={{type="control",id="reset"}}}
  }
})
```

The SDK tags the maintenance view as `category="maintenance"`, `persistent=true`, `textOnly=true` and publishes it in the same app descriptor. Both common renderers expose a maintenance navigation action; selecting it switches to the text renderer even on CC:Graphics machines. The text view provides an automatic return-to-app action. The application calls `app:touch(result,x,y)` and redraws; there is no per-app coordinate calculation. `app:showView(id)` also changes active view programmatically.

A **preset installs and launches the app**; the maintenance interface is owned by the application, not defined in the preset manifest. This API does not provide access controls or confirmation by itself: dangerous operations must remain guarded in their Lua callbacks, and remote execution is not yet wired.

Still to validate in-game: screen size and touch coordinates for graphics/text transition, performance, and preset lifecycle. No production/native app has been migrated in this slice.
