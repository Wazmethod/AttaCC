# AttaCC 1.1 SDK — First Implementation

**Branch:** `feature/v1.1-sdk-unification`. This is an initial functional facade, **not** the completed declarative renderer or network control layer.

## Native CraftOS vs AttaCC

| CraftOS primitives | AttaCC facade |
|---|---|
| `os.pullEvent()` and `os.queueEvent()` | `app:on()`, `app:emit()`, `app:handle()` |
| `term`, monitors and CC:Graphics | `app:view()` declares a portable *descriptor*; automatic rendering not yet implemented |
| `peripheral`, `redstone`, `modem` | Existing `lib.io_registry` / `lib.network`; facade integration to follow |
| Plain Lua variables | `app:data()`, `app:set()`, `app:values()` |
| Function calls | `app:control()`, `app:invoke()` (local only) |
| CraftOS print/files | `app:log()`, `app:status()` |

## Minimal API

```lua
local attacc = require("lib.attacc")
local app = attacc.app("elevator", {title="Elevator"})
app:data("floor", {label="Current floor", value=1})
app:data("moving", {label="Moving", value=false})
app:control("floor_1", {label="Go to 1", run=function() app:set("floor", 1) end})
app:view("main", { data={"floor","moving"}, controls={"floor_1"} })
app:publish()
app:invoke("floor_1") -- local trusted Lua only
app:publish() -- push updated values; automatic reactivity is not yet implemented
```

## Actual implemented calls

- `attacc.app(id, {title=...})` creates an in-memory application descriptor.
- `app:data(id, {label, unit, value, read})` declares a metric. `read` is an optional callback invoked during snapshot building.
- `app:set(id, value)` updates a metric's stored value.
- `app:control(id, {label, description, run})` declares a local callback.
- `app:invoke(id, ...)` executes a **locally trusted** callback with error logging. Remote actions are **not** wired to this method.
- `app:view(id, {label, layout, data, controls})` declares a named view.
- `app:descriptor()` builds serializable data; no functions are exported.
- `app:publish()` publishes the descriptor via existing `lib.webcap` and optionally `lib.display_api` when the display package is installed.
- `app:on(topic, handler)`, `app:emit(topic, payload)`, `app:handle(event, ...)` wrap the current local event bus. Events still need explicit dispatch in the CraftOS main loop.
- `app:status(state, detail)`, `app:log(level, message)` wrap `lib.runtime`.
- `app:close()` unsubscribes local handlers and clears published data owned by this app.

## Explicit limitations

1. `app:view()` does **not** draw buttons to a monitor yet.
2. `webcap` publication does **not** automatically create WebUI widgets or remote controls.
3. `app:invoke()` must not be bound directly to untrusted network traffic. Authentication, target validation, limits and acknowledgments are a separate upcoming step.
4. Data must be republished when values change; automatic subscriptions are future work.
5. The descriptor is written by `display_api` with a single current owner. Multi-app composition is not yet implemented.
6. This does not change SteamPlant, Master, Pocket, Dashboard or other existing apps.

## Testing

Install the branch's `core.runtime` package on a **spare CC** using a test repository. Copy `examples/sdk-elevator/main.lua` to `elevator-demo.lua`, then run `elevator-demo`. Press 1/2/3, observe logs with `logctl tail 20 app:elevator`, and verify the published capability in the machine snapshot. Press Q to clean up. A monitor UI is not expected yet.

## Declarative display interactions (incremental V1.1)

The generic text renderer computes hitboxes from declared `control` nodes; applications no longer need to maintain button-coordinate maps. Its footer creates touch targets for pagination when more than one page exists; `app:touch(result, x, y)` updates `app.displayPage` and the caller redraws. Keyboard and monitor events still need a CraftOS event loop.

`display.toggle` is a **reserved action**, not an application business control. In a generic text view it is only rendered when both `graphicsAvailable = true` and `onToggleRenderer` (a functioning mode-switch callback) are explicitly passed to `app:draw()`. Do not enable this flag merely because the peripheral claims CC:Graphics support: a real graphics renderer must exist. Otherwise the mode button is hidden. Legacy apps can use `renderer:toggleBackend()` and `renderer:availableBackends()` independently.

Low screen resolution shows a warning and suppresses interactive controls rather than terminating the application. `app:draw()` returns a diagnostic status; optional monitor failures should be handled by falling back to `term.current()` or skipping display. Hardware role declarations through `app:io()` are metadata only until I/O binding integration is completed.

**Still pending:** generic CC:Graphics theme and renderer, I/O monitor binding, live graph widgets, remote controls, full SteamPlant screen migration and automated in-game validation.
